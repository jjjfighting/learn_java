# 学生管理系统 · 第十步：文件元数据落库与重新下载

> 本篇补上第九步文件上传遗留的最后一环：**元数据落库**。上传时把文件名 / 类型 / 大小 / 上传人持久化到 `sys_file` 表，新增**按 ID 重新下载**与**分页列表**两个接口——文件不再是"上传即丢"的一次性资源。全部用例需在你本地联调确认（检查单见第六节）。

## 一、遗留问题：为什么上传后无法重新下载

第九步的上传流程是"落盘即还"：`FileService.store()` 把文件写进磁盘 `uploads/` 目录，返回 `FileVO`（含 `url`）后**什么都不落库**。重新下载完全依赖前端把返回值里的 `url` 手动存进业务字段（如 `student.photo`），由此产生三个断点：

1. **元数据全部丢失**——`originalName / size / contentType / 上传人 / 上传时间` 没有任何表承载。一旦前端没把 URL 关联进业务表（或上传响应丢失），文件就成了不可达的孤儿文件，没有任何途径能查出来"这个文件存在、叫什么、在哪"。
2. **拿不到原始文件名**——即使手握 URL，`view` 接口是 `Content-Disposition: inline`，且 `filename=` 写死成 UUID 磁盘名，用户下载到的是 `a1b2...e09.png` 一串乱码，不是上传时的 `张三的获奖证书.png`。
3. **没有文件清单**——没有表就没有列表接口，"我的上传"管理页无从谈起。

一句话：**文件只有磁盘态，没有"档案"态**。

## 二、方案总览

| 维度 | 做法 |
|---|---|
| 落库 | 上传成功落盘后，把文件参数插入 `sys_file` 表（插库失败则回滚磁盘文件） |
| 下载 | 新增 `GET /files/download/{id}`：查库拿元数据 → 复用路径穿越防护解析磁盘路径 → 以**原始文件名**触发 `attachment` 下载 |
| 列表 | 新增 `GET /files/list`：分页查询，支持按原始文件名模糊、按上传人筛选 |
| 鉴权 | 下载 / 列表走默认登录校验；`/files/view/**` 保持公开供 `<img>` 内联展示 |

## 三、数据库：sys_file 表

**只存元数据，不存文件本体**——延续第九步的设计决策：文件字节流躺在磁盘，库里只放"档案卡"。

```sql
CREATE TABLE sys_file (
    id            BIGINT        NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    original_name VARCHAR(255)  NOT NULL                COMMENT '原始文件名（下载/展示用）',
    stored_name   VARCHAR(64)   NOT NULL                COMMENT '磁盘存储名：UUID.扩展名',
    content_type  VARCHAR(100)  NOT NULL                COMMENT '文件 MIME 类型',
    size          BIGINT        NOT NULL                COMMENT '文件大小（字节）',
    uploaded_by   BIGINT        DEFAULT NULL            COMMENT '上传人ID（外键 -> sys_user.id）',
    create_time   DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '上传时间',
    deleted       TINYINT       NOT NULL DEFAULT 0      COMMENT '逻辑删除：0未删除 1已删除',
    PRIMARY KEY (id),
    UNIQUE KEY uk_stored_name (stored_name),   -- UUID 名天然唯一，顺手做唯一键兜底
    KEY idx_uploaded_by (uploaded_by),
    CONSTRAINT fk_file_uploader
        FOREIGN KEY (uploaded_by) REFERENCES sys_user (id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '文件表';
```

两个命名决策：

- **表名 `sys_file` 而非 `file`**：既避开与 `java.io.File` 撞名，也规避 MySQL `FILE` 关键字的歧义；
- **`stored_name` 设唯一键**：UUID 名理论唯一，唯一键是防止并发下重复的兜底防线。

数据库演进沿用第九步定下的双维护规范：**全新环境**跑 `sql/init.sql`（全量，已同步加入该表）；**已有环境**跑 `sql/10-file-table.sql`（增量，`CREATE TABLE IF NOT EXISTS`）。

## 四、后端改动

### 4.1 实体与 Mapper

实体类不碰文件字节流，只映射档案字段；`deleted` 打 `@JsonIgnore`，逻辑删除由 yml 全局配置自动生效（`selectById` 自动过滤已删除记录）。

```java
@Data
@TableName("sys_file")
public class SysFile implements Serializable {
    @TableId(type = IdType.AUTO)
    private Long id;
    private String originalName;
    private String storedName;
    private String contentType;
    private Long size;
    private Long uploadedBy;
    @TableField(fill = FieldFill.INSERT)
    private LocalDateTime createTime;
    @JsonIgnore
    private Integer deleted;
}
```

```java
public interface SysFileMapper extends BaseMapper<SysFile> { }
```

### 4.2 FileService：落库 + 回滚 + 查询

`store()` 在原有安全四件套（空文件 / 白名单 / UUID 改名 / 落盘）之后新增第五步落库，**顺序是先落盘、再落库**：

```java
// ⑤ 元数据落库；插入失败必须回滚磁盘文件，避免留下不可达的孤儿文件
SysFile meta = new SysFile();
meta.setOriginalName(original);
meta.setStoredName(storedName);
meta.setContentType(contentType);
meta.setSize(file.getSize());
UserInfo user = UserContext.get();
meta.setUploadedBy(user == null ? null : user.getId());
try {
    fileMapper.insert(meta);
} catch (Exception e) {
    log.error("文件元数据落库失败，回滚磁盘文件：{}", storedName, e);
    try {
        Files.deleteIfExists(storageRoot.resolve(storedName));
    } catch (IOException ex) {
        log.error("回滚磁盘文件失败：{}", storedName, ex);
    }
    throw new BusinessException(ResultCode.INTERNAL_SERVER_ERROR, "文件保存失败");
}
FileVO vo = new FileVO();
vo.setId(meta.getId());   // ← 前端拿到 id，随时重新下载
```

**"先落盘后落库"的意义**：库里只会出现"确实落盘成功"的文件，不会冒出有记录无文件的幽灵记录；反过来，落库失败就删除磁盘文件，保证两边要么都成功、要么都不存在。

另外两个新方法：

- `getMeta(Long id)`——按 ID 查元数据，`selectById` 自动套用逻辑删除过滤；
- `pageFiles(originalName, uploadedBy, pageNum, pageSize)`——`LambdaQueryWrapper` 条件分页，按 `id` 倒序，最新的在前。

### 4.3 FileController：download / list 两个接口

```java
/** 重新下载：按文件ID查元数据，以原始文件名触发下载 */
@GetMapping("/download/{id}")
public void download(@PathVariable Long id, HttpServletResponse response) throws IOException {
    SysFile meta = fileService.getMeta(id);
    if (meta == null) throw new BusinessException(ResultCode.NOT_FOUND, "文件不存在");
    Path file = fileService.resolve(meta.getStoredName());   // 复用路径穿越双闸门
    if (file == null) throw new BusinessException(ResultCode.NOT_FOUND, "文件不存在");
    String contentType = meta.getContentType() != null ? meta.getContentType()
            : Files.probeContentType(file);
    response.setContentType(contentType != null ? contentType : "application/octet-stream");
    // RFC 5987：filename*=UTF-8''... 支持中文原始文件名；ASCII 名走 filename 兜底
    String encoded = URLEncoder.encode(meta.getOriginalName(), StandardCharsets.UTF_8).replace("+", "%20");
    response.setHeader("Content-Disposition",
            "attachment; filename=\"" + encoded + "\"; filename*=UTF-8''" + encoded);
    Files.copy(file, response.getOutputStream());
}

/** 文件列表（分页） */
@GetMapping("/list")
public Result<Page<FileVO>> list(@RequestParam(required = false) String originalName,
                                 @RequestParam(required = false) Long uploadedBy,
                                 @RequestParam(required = false) Integer pageNum,
                                 @RequestParam(required = false) Integer pageSize) {
    return Result.success(fileService.pageFiles(originalName, uploadedBy, pageNum, pageSize));
}
```

### 4.4 鉴权矩阵

| 接口 | 鉴权 | 说明 |
|---|---|---|
| `POST /files/upload` | 需登录 | 不变，仍挂 `@OperationLog` |
| `GET /files/view/{filename}` | **公开** | 白名单 `/files/view/**`，供 `<img>` 内联展示 |
| `GET /files/download/{id}` | 需登录 | 不在白名单，暴露原始文件名比公开的 view 更敏感 |
| `GET /files/list` | 需登录 | 不在白名单 |

想限制"列表仅管理员可见"，给 `list` 加 `@RequireRole("ADMIN")` 即可（参照 `OpLogController`）。

## 五、关键设计决策

1. **按文件 ID 下载，而非磁盘名**——ID 是主键：能查元数据、能还原原始文件名、不暴露存储布局；前端只存一个 `id` 就够。
2. **先落盘后落库 + 失败回滚**——保证"有记录必有文件"，不留孤儿。
3. **`attachment` 与 `inline` 语义分离**——展示走 `view`（内联），下载走 `download`（附件），职责清晰。
4. **中文文件名用 RFC 5987**——`filename*=UTF-8''` 是标准的中文文件名方案，`filename="..."` 只做 ASCII 兜底。
5. **表名避开关键字**——`sys_file` 不撞 `java.io.File` 与 MySQL `FILE`。

## 七、高频坑位

1. **`Page.convert()` 返回 `IPage<R>`，不是 `Page<R>`**——本次实测踩的坑：`return page.convert(this::toVO)` 编译报错（返回类型不兼容）。正确写法是手动构造新 Page：
   ```java
   Page<FileVO> voPage = new Page<>(page.getCurrent(), page.getSize(), page.getTotal());
   voPage.setRecords(page.getRecords().stream().map(this::toVO).collect(Collectors.toList()));
   return voPage;
   ```
2. **curl 上传被白名单拒**：`-F "file=@a.png"` 默认带 `application/octet-stream`，要 `-F "file=@a.png;type=image/png"` 显式指定（浏览器无此问题）。
3. **`Content-Disposition` 中文乱码**：`filename="张三.png"` 直接拼进去会被浏览器按 Latin-1 误解码，必须用 `filename*=UTF-8''`。
4. **逻辑删除后磁盘文件残留**：记录删了，`uploads/` 里的文件还在。本期不处理，留作后续清理任务（定时任务扫描 `sys_file` 之外的磁盘文件）。
5. **落库失败必须回滚磁盘**：`store()` 里插入 `sys_file` 失败却不删磁盘文件，就造出一个前端永远查不到、磁盘上永远删不掉的孤儿。
