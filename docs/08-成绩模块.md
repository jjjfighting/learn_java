# 学生管理系统 · 第八步：成绩模块 CRUD（五张业务表收官）

> 本篇完成：成绩模块全套——录入成绩（联合唯一键的三重防护，含"逻辑删除 × 唯一键"的墓碑问题破解）、按学生 / 按课程两个维度查询（动态 SQL 首秀）、聚合统计（平均分 / 最高分 / 总分 / 最低分）、录入改删限制 TEACHER/ADMIN 角色。19 个联调用例实测通过。至此 `sys_user`、`clazz`、`course`、`student`、`score` 五张业务表全部完成。

## 一、中间表模块的特殊性

成绩表是 `student` 和 `course` 的中间表（多对多拆解），它和前三个单表模块有三点不同，恰好构成本步的三个主题：

1. **联合唯一键** `uk_student_course (student_id, course_id)`：一名学生一门课只有一条成绩——催生了本步最硬核的"三重防护 + 墓碑清理"；
2. **所有展示都需要回显两端信息**：光给前端 `studentId:1, courseId:2` 没有可读性——催生了 JOIN 列表 + 动态条件 SQL；
3. **天然是统计对象**：成绩单要算平均分、最高分——催生了聚合函数实战。

文件清单里 `entity/Score.java` 和 `mapper/ScoreMapper.java` 在第六步已建骨架，本步补全；新增 `ScoreService(+Impl)`、`ScoreController`、三个 VO（`ScoreVO`、`StudentScoreStatsVO`、`CourseScoreStatsVO`）。

## 二、联合唯一键的三重防护（本步核心）

数据库的 `uk_student_course` 是最后一道闸，但只靠它有三个问题：报错信息不友好、并发下体验差、**和逻辑删除打架**。所以设计成三层：

```
录入请求
 ├─ 第一层 Service 预检：lambdaQuery().eq(studentId).eq(courseId).exists()
 │    命中 -> 4001 "学生 张三 在《MySQL数据库》已有成绩，请使用修改接口"（提示语带姓名课名）
 ├─ 第二层 墓碑清理：physicallyDeleteTombstone(studentId, courseId)   ← 见下文
 └─ 第三层 数据库兜底：并发双发时，后落库的被唯一索引拒绝
      -> DuplicateKeyException -> 全局处理器转 400 "数据已存在，请勿重复提交"
```

**第三层有个继承关系细节**：`DuplicateKeyException` 是 `DataIntegrityViolationException` 的子类（后者在第六步已处理外键冲突）。全局处理器里两个方法并存不会冲突——Spring 按"最具体的异常类型优先"匹配，唯一键冲突走专用分支，其余约束走通用分支。

**预检和兜底为什么都要留？** 预检解决 99% 的常规重复（友好提示），兜底解决 1% 的并发穿透（两个请求同时通过预检，中间有毫秒级窗口）。省掉预检，用户体验差；省掉兜底，并发下有脏数据——两层各司其职。

### 逻辑删除 × 唯一键：墓碑问题

这是本步最大的坑，单独讲。设想正常操作流：

```
给张三录入 MySQL 课成绩 -> 删除这条成绩 -> 重新给张三录 MySQL 课成绩
```

第三步会**莫名其妙失败**。原因：唯一键约束建在**物理行**上，而"删除"只是 `UPDATE deleted=1`——那条旧记录（墓碑）还原封不动躺在表里占着 `(1, 2)` 这个唯一键位置。于是重新 INSERT `(1, 2)` 时，数据库看到"已存在"，拒绝。

更刁钻的是：Service 的预检查询自带 `deleted=0` 过滤，查不到墓碑，判定"不重复"，放行——然后在第三层被数据库背刺。

解法是在录入前加一步**墓碑清理**：

```java
// ScoreMapper
@Delete("DELETE FROM score WHERE student_id = #{studentId} AND course_id = #{courseId} AND deleted = 1")
int physicallyDeleteTombstone(@Param("studentId") Long studentId, @Param("courseId") Long courseId);
```

语义是："这个组合的历史记录反正已经删了，物理清掉给新记录腾出唯一键位置。"平时无墓碑时这条 DELETE 影响 0 行，无副作用。

> 这是逻辑删除方案的固有代价：**唯一键、外键这类建在物理行上的约束，都不理解 `deleted` 标志**。遇到一处就要专门处理一处——本项目里外键那边（班级/课程删除保护）是靠业务预检绕开的，唯一键这边是靠墓碑清理解决的。

实测验证：`P16 删除成绩5 -> 200`，紧接着 `P17 同组合重录 -> 200（新id=7）`，控制台能看到清理 SQL 先执行：

```sql
DELETE FROM score WHERE student_id = ? AND course_id = ? AND deleted = 1
-- Parameters: 1(Long), 2(Long)
```

## 三、两维度查询：动态 SQL 首秀

一个列表接口承担两个维度：`GET /scores?studentId=1`（某学生成绩单）和 `GET /scores?courseId=1`（某课程成绩表），规则是**至少传一个**，都不传返回 `400 请至少指定一个查询维度`——防止误查全表。

条件随参数变化、又必须 JOIN 两张表回显姓名课名——`LambdaQueryWrapper` 管不了 JOIN，于是本项目第一次用上**动态 SQL**：

```java
@Select("""
        <script>
        SELECT s.id, s.student_id, s.course_id, s.score, s.exam_time, s.create_time, s.update_time,
               st.name AS student_name, st.student_no AS student_no,
               c.course_name AS course_name
        FROM score s
        LEFT JOIN student st ON st.id = s.student_id AND st.deleted = 0
        LEFT JOIN course c  ON c.id  = s.course_id  AND c.deleted = 0
        WHERE s.deleted = 0
        <if test="studentId != null"> AND s.student_id = #{studentId} </if>
        <if test="courseId  != null"> AND s.course_id  = #{courseId} </if>
        ORDER BY s.id DESC
        </script>
        """)
List<ScoreVO> selectScoreList(@Param("studentId") Long studentId,
                              @Param("courseId") Long courseId);
```

三个知识点：

1. **`@Select` 里写 `<script>` 就能嵌 MyBatis XML 标签**，`<if>` 的 `test` 表达式为真才拼接该段——和条件构造器的三参数重载同一个思想，只是换了载体；
2. **`#{param}` 是预编译参数绑定**（生成 `?` 占位符，防 SQL 注入），多参数时用 `@Param("名字")` 起名，`test` 和 `#{}` 里引用的就是这个名字；
3. **老规矩第四次强调**：三张表的 `deleted=0` 全部手写，`st.deleted=0` 放 `ON` 里不放 `WHERE` 里。

控制台日志里能看到按学生维度实际执行的 SQL 只拼了一个条件：

```sql
... WHERE s.deleted = 0 AND s.student_id = ? ORDER BY s.id DESC
-- Parameters: 1(Long)
```

## 四、聚合统计：让数据库把活干完

两个统计接口，SQL 是聚合函数全家桶：

```sql
-- GET /scores/stats/by-student?studentId=1
SELECT s.student_id, st.name AS student_name,
       COUNT(s.score) AS course_count,          -- 已判分科目数
       ROUND(AVG(s.score), 2) AS avg_score,     -- 平均分保留两位
       MAX(s.score) AS max_score,
       SUM(s.score) AS total_score
FROM score s LEFT JOIN student st ON st.id = s.student_id AND st.deleted = 0
WHERE s.deleted = 0 AND s.student_id = #{studentId}
```

五个要点：

| 点 | 说明 |
|---|---|
| `COUNT(s.score)` ≠ `COUNT(*)` | `score` 列允许 null（先建记录后判分）；`COUNT(*)` 数行数，`COUNT(列)` 不数 null 行——这里要的是"已判分科目数" |
| `AVG` 自动忽略 null | 未判分记录不会把平均分拉低，这是 SQL 语义，但要知道 |
| `ROUND(AVG(...), 2)` | 平均分天然是长小数，数据库侧截好两位再出来，别把精度处理丢给前端 |
| **不带 `GROUP BY` 的聚合永远返回一行** | 该生一条成绩都没有时，返回 `course_count=0, avg_score=null` 的一行，而不是空结果集——Service 据此直接返回，前端显示"暂无成绩" |
| 聚合结果直接映射 VO | 别名 `avg_score` 经下划线转驼峰落到 `StudentScoreStatsVO.avgScore`（BigDecimal），Java 侧不做任何二次计算 |

实测：张三两科 92.50 + 88.50 →

```json
{"studentId":1,"studentName":"张三","courseCount":2,"avgScore":90.50,"maxScore":92.50,"totalScore":181.00}
```

原则一句话：**能在数据库算完的，不要搬到内存里算**——数据库为聚合做了专门优化，应用层循环累加既慢又啰嗦。

## 五、校验的差异化：为什么这次放业务层

前几个模块的必填校验都挂在实体注解上，这次 `studentId`/`courseId` 的必填却写在了 Service 里：

```java
if (score.getStudentId() == null) {
    throw new BusinessException(ResultCode.BAD_REQUEST, "学生ID不能为空");
}
```

原因是**新增和修改对同一字段的规则相反**：录入时 `studentId`/`courseId` 必填；修改时这俩字段根本不许动——成绩记录由"谁 + 哪门课"定义，改分数才是修改，改归属应该走"删除 + 重新录入"。注解是"一刀切"的，做不到这种差异化，于是 `updateScore` 里干脆从库记录出发：

```java
Score db = this.getById(id);            // 归属信息以数据库为准
db.setScore(score.getScore());          // 只接受分数
db.setExamTime(score.getExamTime());    // 和考试日期
this.updateById(db);                    // 请求体里偷塞 studentId 也无效
```

沉淀成原则：**增改规则一致 → 注解；增改规则分叉 → 业务层**。

## 六、角色控制的细化：多角色数组

成绩写操作的注解从单个角色升级成了角色数组：

```java
@RequireRole({"TEACHER", "ADMIN"})
@PostMapping
public Result<Long> add(@Valid @RequestBody Score score) { ... }
```

拦截器里 `Arrays.asList(required.value()).contains(user.getRole())` 天然支持多角色——这是第七步预留的设计，本步第一次用上。权限语义很自然：**教师和管理员都能录分改分，其他角色只能看**。

顺带说清两层校验的分工：`@RequireRole` 管"**谁有资格录成绩**"（身份），Service 的存在性/查重校验管"**这条成绩能不能录**"（数据）——一层都少不了。

## 八、高频坑位

1. **唯一键 + 逻辑删除 = 墓碑**：本项目最隐蔽的一个坑。凡是"逻辑删除 + 唯一键"的表，都要问一句：删了之后能不能重建？不能就要设计墓碑清理或改用物理删除；
2. **`COUNT(*)` vs `COUNT(列)`**：列含 null 时两者结果不同，按"数行数"还是"数有值行"选择；
3. **聚合查询没有空结果集**：不带 GROUP BY 的聚合永远返回一行，判"有没有数据"要看 `COUNT` 值或 `AVG` 是否为 null，不能判"结果集为空"；
4. **自定义 SQL 的 `deleted=0`**：第四次强调了——JOIN 的每张表都要写，被连接表的写 ON 里；
5. **`BigDecimal` 比较**：统计值展示和比较一律 `compareTo()`，`equals` 会把 `90.50` 和 `90.5` 判成不相等；
6. **预检不能替代兜底，兜底不能替代预检**：并发窗口客观存在（预检到落库之间），唯一键/外键的数据库防线永远要留；反过来只靠数据库报错，用户看到的就是天书。
