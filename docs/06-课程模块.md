## 二、教师回显：关联处理③的两种形态

同一个需求"列表/详情里显示关联名称"，本模块同时出现了两种实现，正好做个对照：

**列表——一条 JOIN SQL 批量带出**（`CourseMapper`）：

```sql
SELECT c.id, c.course_name, c.credit, c.teacher_id, c.description, c.create_time, c.update_time,
       u.real_name AS teacher_name
FROM course c
LEFT JOIN sys_user u ON u.id = c.teacher_id AND u.deleted = 0
WHERE c.deleted = 0
ORDER BY c.id DESC
```

**详情——两次简单查询拼装**（`CourseServiceImpl#getCourse`）：先 `getById` 拿课程，再 `userMapper.selectById` 拿教师，`BeanUtils.copyProperties` 拷进 `CourseVO` 补上 `teacherName`。

取舍标准：**列表批量回显用 JOIN（一次往返），单条详情用两次查询（代码直白、关联点少）**。第五步学生详情用的是后者，班级列表用的是前者，到这里两种形态都集齐了。JOIN 写法的两个老规矩不变：`u.deleted=0` 写在 `ON` 里、自定义 SQL 的删除过滤全部手写。

实测列表响应：

```json
{"code":200,"message":"操作成功","data":[
  {"id":2,"courseName":"MySQL数据库","credit":3.0,"teacherId":2,"teacherName":"王老师",...},
  {"id":1,"courseName":"Java程序设计","credit":4.0,"teacherId":2,"teacherName":"王老师",...}
]}
```

## 三、教师资质校验：外键挡不住的那一半

`teacher_id` 上有外键 `fk_course_teacher` 指向 `sys_user.id`，但外键只能保证"**引用的用户存在**"，保证不了"**这个用户有资格当老师**"——把管理员 `admin` 设成授课教师，数据库照样放行。这类**语义正确性**必须业务层兜住：

```java
private void checkTeacher(Long teacherId) {
    if (teacherId == null) return;                       // 允许暂不指定教师
    SysUser user = userMapper.selectById(teacherId);
    if (user == null) {
        throw new BusinessException(ResultCode.USER_NOT_FOUND, "授课教师不存在（ID=" + teacherId + "）");
    }
    if (!ROLE_TEACHER.equals(user.getRole())) {
        throw new BusinessException(ResultCode.TEACHER_ROLE_REQUIRED,
                "用户 " + user.getUsername() + " 的角色是 " + user.getRole() + "，不是教师");
    }
}
```

实测把 `teacherId` 填成管理员（id=1）：

```json
{"code":1004,"message":"用户 admin 的角色是 ADMIN，不是教师","data":null}
```

把这个思路沉淀成一句结论：**数据库约束管"数据完整性"（存在性、唯一性、非空），业务层管"语义正确性"（角色、状态、流程）**，两道防线各管一半，谁也别替谁背书。

## 四、删除保护：为什么成绩表的两条外键行为相反

翻一下建表脚本会发现一个有意思的对比：

```sql
-- 成绩表的两条外键，删除行为故意设计成不同的
CONSTRAINT fk_score_student FOREIGN KEY (student_id) REFERENCES student (id)
    ON DELETE CASCADE,   -- 删学生 -> 成绩自动清掉（成绩依附于学生存在）
CONSTRAINT fk_score_course FOREIGN KEY (course_id) REFERENCES course (id)
                         -- 默认 RESTRICT：有成绩记录 -> 禁止删课程（成绩是教学成果，不能随课程蒸发）
```

对应到 Service 层，删课程前统计成绩条数，给出友好提示：

```java
Long count = scoreMapper.selectCount(
        new LambdaQueryWrapper<Score>().eq(Score::getCourseId, id));
if (count > 0) {
    throw new BusinessException(ResultCode.COURSE_HAS_SCORES,
            "该课程已有 " + count + " 条成绩记录，请先处理成绩后再删除");
}
```

实测：`{"code":3004,"message":"该课程已有 2 条成绩记录，请先处理成绩后再删除"}`。和班级模块一样：业务预检给友好提示，数据库 RESTRICT 当最后防线。

## 五、学分为什么用 BigDecimal

`credit` 是 `DECIMAL(3,1)`，Java 侧必须用 `BigDecimal` 而不是 `double`：`double` 是二进制浮点，`0.1 + 0.2 != 0.3` 这种误差对分数、金额是致命的。配套两条规则：

1. 实体上用 `@Digits(integer = 2, fraction = 1)` + `@DecimalMin("0.0")` 校验格式，实测传 `-1` 返回 `400 credit: 学分不能为负`；
2. 以后比较大小用 `compareTo()`，**绝不用 `equals()`**——`new BigDecimal("3.0").equals(new BigDecimal("3.00"))` 是 `false`（精度不同），这是 BigDecimal 最经典的坑。

## 七、高频坑位

1. **外键迷信**：外键只保证引用存在，"引用的对象是否合格"（角色、状态）永远在业务层校验；
2. **JOIN 回显忘了 `deleted=0`**：第三次强调——自定义 SQL 里每张参与表的逻辑删除过滤都要手写，漏掉教师的 `u.deleted=0`，已注销教师的名字照样回显出来；
3. **`BigDecimal.equals` 比较**：比大小永远 `compareTo() == 0`；
4. **回显字段的数据新鲜度**：`teacherName` 是查询那一刻的快照，教师改名后旧缓存/旧列表不会自动更新——VO 回显的本质是"冗余换性能"，要接受这一点；
5. **COUNT 统计与删除策略一致**：成绩计数自动带 `deleted=0`（框架生成 SQL），与课程列表手写 `deleted=0` 口径一致，两边才不会"列表说没有、删除说有"。
