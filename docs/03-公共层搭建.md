# 学生管理系统 · 第三步：搭建公共层

> 本篇完成：统一返回类 `Result`、返回码枚举 `ResultCode`、自定义业务异常 + 全局异常处理器 `@RestControllerAdvice`、MyBatis-Plus 公共字段自动填充（create_time/update_time），并用一个测试 Controller 验证了四种返回场景。这是后面所有模块的地基。

## 一、为什么先搭公共层

如果直接写业务模块，很快会发现三件重复到令人崩溃的事：

1. **每个接口都要拼返回格式**——这个接口返回 `{"msg":...}`，那个返回 `{"status":...}`，前端没法统一解析；
2. **每个 Controller 都要写 try/catch**——漏写一个，前端就收到 Tomcat 的 HTML 错误页；
3. **每条新增/修改都要手写 `setCreateTime(LocalDateTime.now())`**——几十张表就是几百行废话。

公共层就是把这三件事一次性解决，之后所有模块"免费"获得：统一 JSON 格式、异常自动兜底、时间字段自动填充。

## 三、统一返回类 Result

约定所有接口都返回同一种 JSON 形状，前端只需要写一套解析逻辑：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": { "project": "学生管理系统" }
}
```

### 关键设计讲解

**1. 泛型 `<T>`**：`data` 的类型由调用方决定——`Result<Student>`、`Result<List<Student>>` 都用同一个类，编译期就能检查类型。

**2. 私有构造 + 静态工厂**：构造器全部私有，只能通过 `Result.success(...)` / `Result.error(...)` 创建对象。好处是返回格式被"焊死"了，没人能 new 出一个缺字段的 Result。

**3. `error` 方法也带 `<T>`**：方法签名是 `Result<Student> getById(...)` 时，失败分支可以直接 `return Result.error(...)`，不用强转。

**4. 实现 `Serializable`**：将来把返回对象放进 Session、Redis 缓存或走 RPC 时不会被序列化卡住，属于低成本的前瞻设计。

> 💡 注意：所有响应（包括错误）的 **HTTP 状态码都是 200**，成败由响应体里的 `code` 表达。前端只判断 `body.code` 一个渠道即可，不用同时处理 HTTP 层和 body 层两套错误——这是国内业务系统常见约定。

## 四、返回码枚举 ResultCode

码值集中管理，杜绝魔法数字满天飞（比如某天想知道"1002 是啥意思"，全局搜数字要搜到手软）。

编码约定：

| 码段 | 含义 | 例子 |
|---|---|---|
| `200` | 成功 | 对齐 HTTP 语义，直觉一致 |
| `400~499` | 客户端错误 | 400 参数错误 / 401 未登录 / 403 无权限 / 404 资源不存在 |
| `500` | 服务器错误 | 兜底异常统一返回 |
| 4 位业务码 | 业务错误，第 1 位是模块号 | `1xxx` 用户 / `2xxx` 学生 / `3xxx` 班级课程 / `4xxx` 成绩 |

枚举的 `@Getter` + `final` 字段组合是固定写法：枚举实例创建后码值不可改，线程安全。

以后新增错误码只需要在枚举里加一行，比如学生模块后续可能加 `STUDENT_NO_ALREADY_EXISTS(2002, "学号已存在")`（已经提前占位了）。

## 五、自定义业务异常 BusinessException

业务代码表达"规则不满足"的方式：**抛异常，而不是返回 null**。对比一下：

```java
// ❌ 返回 null：调用方必须记得判空，忘了就是 NPE，错误信息也丢了
public Student getById(Long id) {
    return studentMapper.selectById(id);  // 查不到返回 null
}

// ✅ 抛业务异常：语义明确，全局处理器统一转 JSON，调用方无需判空
public Student getById(Long id) {
    Student s = studentMapper.selectById(id);
    if (s == null) {
        throw new BusinessException(ResultCode.STUDENT_NOT_FOUND);
    }
    return s;
}
```

**为什么继承 `RuntimeException` 而不是 `Exception`？**

- `Exception` 是受检异常：抛出后编译器强制你 try/catch 或在方法签名写 `throws`，业务代码会被异常处理语句淹没；
- `RuntimeException` 是非受检异常：随抛随走，反正最后有全局处理器兜底。Spring 生态（如 `DataAccessException`）也是这么做的。

第二个构造器 `BusinessException(ResultCode, String message)` 用于把提示语具体化：码还是枚举的码（`1002`），提示语从"用户名已存在"变成"用户名 admin 已被注册"——前端按码走逻辑，按 message 做展示。

## 六、全局异常处理器 GlobalExceptionHandler

### 原理

`@RestControllerAdvice` = `@ControllerAdvice` + `@ResponseBody`。它基于 AOP 拦截**所有** `@RestController` 方法抛出的异常，每个 `@ExceptionHandler(Xxx.class)` 方法负责把一类异常转成 `Result`。从此 Controller 里一个 try/catch 都不用写。

### 处理的异常一览

| 处理方法 | 触发场景 | 返回码 |
|---|---|---|
| `BusinessException` | 业务规则不满足（主动抛出） | 异常携带的码，如 2001 |
| `MethodArgumentNotValidException` | `@RequestBody` + `@Valid` 校验失败 | 400 + 具体字段错误 |
| `BindException` | 表单 / Query 参数绑定校验失败 | 400 + 具体字段错误 |
| `ConstraintViolationException` | 方法参数上的 `@NotBlank`/`@Min` 等单参校验失败 | 400 |
| `HttpMessageNotReadableException` | 请求体 JSON 残缺或格式非法 | 400 |
| `Exception`（兜底，必须放最后） | 其他一切未预期的异常 | 500 |

**匹配规则**：Spring 选择参数类型与异常类型**最接近**的处理方法（子类优先于父类），与方法在类里的书写顺序无关。但 `Exception` 兜底处理器在语义上就是"别人都不要的才归我"，放最后是可读性约定。

> 💡 `MethodArgumentNotValidException` 本身就是 `BindException` 的子类，所以两个处理器共存不会冲突——JSON 校验失败走前者，其余绑定失败走后者。

### 日志策略

- **业务异常**：`log.warn` 一行即可。这是预期内的错误（用户输错了而已），打堆栈只会刷屏；
- **未知异常**：`log.error("系统异常", e)` 带完整堆栈。这是 bug 的线索，上线后排查问题全靠它。

实测控制台输出：

```
WARN  c.s.c.e.GlobalExceptionHandler -- 业务异常：code=1002, message=用户名 admin 已被注册
ERROR c.s.c.e.GlobalExceptionHandler -- 系统异常
java.lang.RuntimeException: 模拟一个没有预料到的错误
        at com.studentms.controller.TestController.unknownError(TestController.java:56)
        ...
```

## 七、公共字段自动填充

五张业务表全都有 `create_time` / `update_time`，如果每次 `insert` 前手写：

```java
student.setCreateTime(LocalDateTime.now());
student.setUpdateTime(LocalDateTime.now());
```

就是纯体力活，还容易漏。MyBatis-Plus 的自动填充把这件事变成"声明一次，全局生效"。

### 两步走

**第一步：实体类字段上声明填充时机**（实体类在第四步写，这里先记住写法）：

```java
@TableField(fill = FieldFill.INSERT)          // 仅新增时填
private LocalDateTime createTime;

@TableField(fill = FieldFill.INSERT_UPDATE)   // 新增、更新时都填
private LocalDateTime updateTime;
```

**第二步：注册一个 `MetaObjectHandler` Bean 告诉框架"填什么值"**，就是本步写的 `MyMetaObjectHandler`：

- `insertFill()`：执行 `insert()` / `save()` 时触发，填 `createTime` 和 `updateTime`；
- `updateFill()`：执行 `updateById()` / `update()` 时触发，填 `updateTime`。

### 两个容易踩坑的细节

**1. 自动填充认"实体属性名"，不认数据库列名。** `strictInsertFill(metaObject, "createTime", ...)` 里的 `"createTime"` 是 Java 属性名；它和列名 `create_time` 的对应关系由 yml 里的 `map-underscore-to-camel-case` 负责，两者各司其职，属性名写错不会报错，只会静默不填充。

**2. `strictXxxFill` 只填 null 字段。** 如果业务代码手动 `setCreateTime(...)` 过，自动填充不会覆盖。绝大多数场景这正是想要的；真要强制覆盖就改用 `setFieldValByName(...)`。

### 和数据库默认值是什么关系？

建表脚本里 `create_time` 已经有 `DEFAULT CURRENT_TIMESTAMP`、`update_time` 还有 `ON UPDATE CURRENT_TIMESTAMP`，为什么还要 Java 填充？两者是**双保险**，各管一段：

| 场景 | 谁生效 |
|---|---|
| 走 MyBatis-Plus 的增改 | Java 自动填充（时间会出现在 SQL 日志里，调试可见） |
| 直接在数据库里手工执行 SQL | 数据库 DEFAULT / ON UPDATE 兜底 |
| 换数据库 / 单元测试用内存库（没有默认值） | Java 自动填充兜底 |

保留数据库默认值不亏，删掉 Java 填充会丢可观测性——都要。

## 九、高频坑位

1. **自动填充不生效又不报错**：`MyMetaObjectHandler` 必须有 `@Component`（忘注册 Bean），且实体属性名与填充方法里的字符串完全一致——两个条件缺一个都是静默失效；
2. **在 Controller 里把 BusinessException catch 掉**：全局处理器就永远不会触发，异常处理又回到各写各的。原则：业务异常只抛不接；
3. **想用 HTTP 状态码区分成败**：本项目约定 HTTP 恒为 200，成败看 `body.code`。别两种风格混用，前端会骂人；
4. **校验注解写了却不生效**：`@Valid` 要配合 `@RequestBody`（JSON）或 `@ModelAttribute`（表单）；直接在方法参数上写 `@NotBlank` 则需要在类上加 `@Validated`——对应全局处理器里三个不同的处理方法；
5. **新增错误码随手写数字**：所有码值进 `ResultCode` 枚举，`error(500, "xxx")` 这种裸数字调用留给真正的特殊场景。
