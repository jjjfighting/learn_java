# 学生管理系统 · 第七步：登录认证（JWT + 角色权限）

> 本篇完成：系统从"裸奔接口"进入"按角色访问"阶段。密码由明文升级为 BCrypt 密文存储（含历史密码的自愈升级）、登录签发 JWT、`JwtAuthInterceptor` 统一完成认证（401）与鉴权（403）、`@RequireRole` 注解声明式控制角色权限。24 个联调用例实测通过。

## 一、两个概念：认证与鉴权

- **认证（Authentication）**：你是谁？—— 用户名 + 密码换一张"通行证"（JWT）；
- **鉴权（Authorization）**：你能干什么？—— 持通行证访问接口时，检查角色够不够格。

本步的代码正好一人一半：`AuthService` 负责认证，`JwtAuthInterceptor` 负责鉴权。

## 二、依赖选型：为什么不装 Spring Security

`pom.xml` 里只加了两个东西：

```xml
<!-- JWT 三件套：api 编译期用，impl/jackson 运行期用（scope=runtime） -->
<dependency>io.jsonwebtoken:jjwt-api / jjwt-impl / jjwt-jackson (0.12.6)</dependency>
<!-- 只引加密工具包，不引整套安全框架 -->
<dependency>org.springframework.security:spring-security-crypto</dependency>
```

故意**没有**引入 `spring-boot-starter-security`：它一旦上 classpath 就自动接管整个应用——所有接口默认要登录、弹出表单登录页、响应格式换成它自己的。对现阶段的学习项目来说，用自定义拦截器 + JWT 手写一遍，能看清认证鉴权的每个齿轮；Spring Security 是"全自动生产线"，等需要会话管理、OAuth2、方法级安全这些重武器时再请它出场。`spring-security-crypto` 则是两全其美：只用它的 `BCryptPasswordEncoder`，不触发任何自动配置。

## 三、BCrypt：密码为什么不能明文、也不能 MD5

建库脚本里 `admin/123456` 是明文——这在真实系统里是事故级别的隐患（拖库即全体密码泄露）。那 MD5 哈希总行了吧？也不行：

1. **MD5 太快**：一张显卡每秒能撞几百亿次，弱密码秒破；
2. **彩虹表**：常用密码的 MD5 值早有现成对照表，查表即得。

BCrypt 两个特性专治这两点：**自带随机盐**（同一个密码每次加密结果都不同，彩虹表作废）、**可调的 cost 成本因子**（故意算得慢，`$2a$10$...` 里的 `10` 就是 2^10 轮迭代，暴力破解的成本被拉高几个数量级）。

密文结构拆解（联调中真实产生的一条）：

```
$2a$10$25.Gq6sIJIbCLfluDk2UaeBPoLuJLRsTrMqeM7Div8xUWfJ6RGHhu
 └┬┘ └┬┘ └──────────┬──────────┘└──────────────┬──────────────┘
 算法 cost       22字符随机盐              31字符哈希值
```

校验时 `passwordEncoder.matches(明文, 密文)` 会从密文里取出盐重新计算比对——所以存库只需要这一个字符串。

## 四、历史明文密码的自愈升级

数据库里已经躺着两个明文密码，怎么迁移？停机跑脚本当然可以，但有个更优雅的模式——**登录即迁移**：

```java
private boolean isPasswordMatch(SysUser user, String rawPassword) {
    String stored = user.getPassword();
    boolean isBcrypt = stored.startsWith("$2a$") || stored.startsWith("$2b$") || stored.startsWith("$2y$");
    if (isBcrypt) {
        return passwordEncoder.matches(rawPassword, stored);   // 正常路径：密文比对
    }
    // 明文兼容路径：仅初始化数据会走到这里
    if (!stored.equals(rawPassword)) return false;
    user.setPassword(passwordEncoder.encode(rawPassword));     // 比对成功，顺手升级
    userMapper.updateById(user);
    return true;
}
```

效果：老用户照常输 `123456` 登录，毫无感知；后台 SQL 日志里能看到密码被改写——

```
UPDATE sys_user SET ..., password=? ... WHERE id=?
Parameters: ..., $2a$10$25.Gq6sIJIbCLfluDk2UaeBPoLuJLRsTrMqeM7Div8xUWfJ6RGHhu(String), ...
```

联调实测：`admin` 首次登录走明文分支并升级，**第二次登录立刻走 BCrypt 分支成功**——自愈闭环验证完毕。以后谁登录过谁就升级，库里的明文会自然消亡。

另外两个安全细节：① "用户不存在"和"密码错误"统一返回 `1003 用户名或密码错误`，不帮攻击者枚举出哪些用户名存在；② `SysUser.password` 挂了 `@JsonIgnore`，任何接口都不会把密码序列化出去。

## 五、JWT：无状态令牌的结构与原理

登录成功后服务端签发 JWT，结构是 `header.payload.signature` 三段 Base64 用 `.` 拼接。把联调拿到的真实 token 的 payload 段 Base64 解开就是：

```json
{"sub":"admin","userId":1,"realName":"系统管理员","role":"ADMIN","iat":...,"exp":...}
```

- **payload 是编码不是加密**——任何人都能解开看，所以只放身份标识，绝不放密码；
- **signature 是服务端用密钥对前两段的签名**——改一个字符都过不了验签，这就是令牌不可伪造的原因；
- **服务端不存任何会话**——请求来了只验签名 + 看过期时间（`exp`），天然适合前后端分离和多实例部署。这是它相对传统 Session 的核心优势，代价是"签出去就无法主动作废"，所以有效期不宜过长（本项目 2 小时）。

签发与解析集中在 `JwtUtil`，密钥和有效期来自 yml：

```yaml
auth:
  jwt:
    secret: StudentMs@2026#JwtSecretKeyForHmacSha256!   # HS256 要求 ≥32 字符，生产必须换强随机密钥
    expire-minutes: 120
```

## 六、拦截器：所有接口的统一大门

`JwtAuthInterceptor`（注册于 `WebMvcConfig`，拦截 `/**`，放行 `/auth/login`、`/test/**`、`/error`）三步走：

```
请求进入
  ├─ ① 取 Authorization: Bearer <token>，解析验签
  │     无 token / 篡改 / 过期  -> 写回 {"code":401,"message":"未登录或登录已过期"}，拦截
  ├─ ② 读目标方法上的 @RequireRole，比对令牌里的角色
  │     角色不满足 -> 写回 {"code":403,"message":"权限不足：需要角色 ADMIN，当前角色 TEACHER"}，拦截
  └─ ③ 用户信息存入 UserContext，放行 -> Controller
```

两个实现要点：

1. **拦截器在 Controller 之前执行，拿不到全局异常处理器的便利**，所以 401/403 用注入的 `ObjectMapper` 手工把 `Result` 写成 JSON 响应——复用了同一个序列化器，响应格式与正常接口完全一致；HTTP 状态码保持 200，与全项目"成败只看 `body.code`"的约定对齐；
2. 解析失败**不区分**"无 token / 签名错 / 已过期"，对外统一 401——错误细节是服务端的日志素材，不是给客户端的情报。

## 七、UserContext：ThreadLocal 与必须清理的线程上下文

业务代码随时想知道"当前请求是谁发的"，最干净的做法是线程上下文：

```java
UserContext.set(user);    // 拦截器放行前
UserContext.get();        // Controller/Service 任意位置取用，例如 /auth/me 直接返回它
UserContext.remove();     // afterCompletion 里必定执行
```

`remove()` 不是可选项，是**安全红线**：Tomcat 用线程池复用线程，请求结束不清理，同一线程接手的下一个请求就会 `get()` 到上一个用户——这是真实发生过的越权事故类型。拦截器的 `afterCompletion` 无论 Controller 正常还是抛异常都会执行，清理放在这里最稳。

## 八、角色控制矩阵

`@RequireRole` 是自定义注解（`@Retention(RUNTIME)` 保证运行时可反射读取），拦截器读到就查角色。当前策略：**删除是高危操作，仅 ADMIN；其余读写，登录即可**。

| 接口 | 匿名 | STUDENT/TEACHER | ADMIN |
|---|---|---|---|
| `POST /auth/login` | ✅（白名单） | ✅ | ✅ |
| 各模块 GET 查询 | ❌ 401 | ✅ | ✅ |
| 各模块 POST/PUT 增改 | ❌ 401 | ✅ | ✅ |
| 各模块 `DELETE`（学生/班级/课程） | ❌ 401 | ❌ 403 | ✅ |

实测两个对照：教师 token 删课程 → `{"code":403,"message":"权限不足：需要角色 ADMIN，当前角色 TEACHER"}`；换管理员 token 删同一课程 → 200。注意 403 出现在**拦截器层**，`CourseServiceImpl` 的业务代码一行都没执行。

## 十、高频坑位

1. **ThreadLocal 不清理 = 串号越权**：set / remove 必须成对，清理放在 `afterCompletion`（见第七节）；
2. **JWT payload 当保险箱**：Base64 ≠ 加密，令牌里的内容假设"全世界都看得到"；
3. **密钥太短**：HS256 要求密钥 ≥256 位，`Keys.hmacShaKeyFor` 遇到短密钥直接启动后抛 `WeakKeyException`；密钥写死在代码里同样危险，生产应从环境变量读；
4. **把 401 和 403 搞混**：401 = 没带/带错身份证（未认证），403 = 身份证是真的但级别不够（未授权），前端处理逻辑完全不同；
5. **密码比对用 `==` 或自己拼 MD5**：永远 `passwordEncoder.matches()`；同时记住 BCrypt 每次加密结果都不同，**不能**拿两次加密结果互相比；
6. **异常信息当情报**：登录失败不区分"用户不存在/密码错误"，token 失效不区分"篡改/过期"——给客户端的错误越模糊越安全，细节留给服务端日志。

## 十一、生产环境还差什么（诚实清单）

本项目是学习系统，以下这些上线前必须补齐，先记个账：

- **HTTPS**：token 走明文 HTTP 等于在广播密码，TLS 是认证体系的地基；
- **令牌刷新**：2 小时过期后强制重登体验差，生产要加 refresh token 双令牌机制；
- **密钥管理**：secret 进配置中心 / 环境变量，不进 Git；
- **密码策略**：注册时的强度校验、失败次数锁定、验证码；
- **审计日志**：谁在什么时候删了什么，安全事件的追溯依据。
